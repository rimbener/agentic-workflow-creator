# Changing a workflow package

Every `workflows/<name>/` folder is a **workflow package**, generated by `awc`
(agentic-workflow-creator) from an interview and possibly hand-edited since.
Every file in it is someone's decision.

- `<name>.yaml` — the workflow: an ordered list of tiny nodes that a
  `workflow_lead` agent walks top to bottom.
- `agents/` — the prompt files the nodes invoke. `workflow_lead.md` is the
  lead's own role.
- `scripts/` — one command each.
- `running.md` — the execution contract: what every key in the YAML means
  and how the lead executes it.
- `README.md` — purpose, node walkthrough, how to launch.

Around it at the repo root sit its launchers: `.claude/commands/<name>.md`,
`.codex/skills/<name>/SKILL.md` and `.opencode/command/<name>.md` start a run
in session, and a worktree workflow adds `./<name>.sh` with
`./agents-cli.conf`.

Read the package's own `running.md` before changing anything. It defines the
dialect and outranks this file wherever they differ; this file is the
checklist that keeps a change from breaking the next run.

## First: which kind of change is this

| The ask | Where it belongs |
| --- | --- |
| A contained change — a cap, a command, a var's value, a prompt's wording, a README row, a script a node runs | Here, by the rules below |
| A change that ripples — an input, a phase, the builder/reviewer pairing, a rename, isolation, an agent's modes | `awc <agent> --edit`, in a fresh session: it loads the agent bases and the full validation checklist, and lands every ripple |
| "Is this package still current?", a run that halts where the YAML looks right, a `running.md` or `workflow_lead.md` that differs from a newer package's | `awc <agent> --upgrade`: an audit against the current dialect, then the migrations it names |
| A new workflow | `awc <agent>` |
| Running the workflow on a task | Its launchers, above — the package does not change |

`<agent>` is `claude`, `codex` or `opencode`; `awc` runs as
`npx agentic-workflow-creator` where it is not installed. The second row can
be done by hand too — the ripple table below is what makes that safe, and
the validation at the end is what proves it.

## Files that are copies — never edit them by hand

These are verbatim copies of awc's own bases. `awc <agent> --upgrade`
refreshes them, and a hand-edit is drift the next upgrade undoes:

- `running.md`
- `agents/workflow_lead.md` — the one agent no package tailors; it outranks
  `running.md` at run time
- `scripts/finish-task.sh` and `scripts/write-verdict-file.sh`
- `./agents-cli.conf`, and `./<name>.sh` below its FILL block
  (`__WORKTREE_PARENT__` is the only value that belongs to the package)
- this skill's own copies under `.claude/skills/`, `.codex/skills/` and
  `.opencode/skill/`

A fix one of them seems to need is a change to awc, not to this package.
Say so instead of patching the copy.

## Rules per file

### The YAML

- **One behavior per node**: `run:`, `agent:` + `prompt:`, `inline:`,
  `loop:`, `gate:` or `wait:`. `parallel: true`, `allowed_tools:` and
  `when:` are modifiers, never a second behavior.
- **`run:` is one short command**, executed from the launch directory — so a
  script path reads `workflows/<name>/scripts/<file>` — and it prints only on
  failure. More than one line of logic is a script.
- **Every `loop:` carries `max_iterations`** and exactly one of `until:` or
  `until_run:`. The `until:` token is honored from the loop's *last* agent
  step only; `until_run:` checks reality (a tool's output, a diff) and is the
  form for a check no agent should be able to pass by asserting. Hitting the
  cap halts the run — that halt is the escalation, so keep caps honest.
- **`inline:` holds `agent:`, `prompt:` and `expect:` only.** It is the node
  for a conversation with the human — an interview above all — because a
  spawned agent can ask one question per spawn while the lead, acting as the
  agent inline, asks and hears answers within one node. An approval round
  (present, hear yes/no, close with a token) stays a loop.
- **`parallel: true` only on a top-level `run:` or `agent:` node** whose work
  shares no writes and needs no human, and a `wait:` naming it sits before
  any node that depends on the result.
- **`allowed_tools:` only on an `agent:` node or agent step**, as capability
  names: `read`, `search`, `edit`, `shell`, `web`, `spawn`. Grant everything
  the agent file does — `shell` for a `Commands:` argument or the verdict
  writer, `edit` for any report it writes, `web` always. A scope drawn too
  tight halts the run as `blocked`; omitting the key is the norm.
- **Every `{{placeholder}}` is declared**: an input, a var, or
  `{{iteration}}` / `{{answer}}` inside a loop body.
- **Open the agent file before touching its node.** Its invocation section
  lists the arguments it requires (`Task:`, `Mode:`, `Commands:`, `Base:`,
  `Verdict-writer:`, …) and the signals it returns; the node passes every
  argument and `expect:` names those signals.
- **`finish` stays last among the trail nodes.** The node running
  `workflows/<name>/scripts/finish-task.sh {{task}}` archives
  `.awc/tasks/in-progress/<task>/`; every node that reads or writes that
  trail — including a `wait:` on parallel work that does — comes before it,
  and only a committer or a push may follow.
- **Gates are structural.** A human sign-off is a `gate:` or an approval
  loop; an un-gameable check is an `until_run:` or `when:` script reading a
  tool's own output. Never a step where an agent passes itself.

### Agents

- **A copy stays argument-driven and project-agnostic.** The YAML owns
  orchestration and pairing; the agent file says how to do one step. Project
  facts arrive as arguments (`Commands:`, `Base:`, `Report:`), never
  hard-coded into the file.
- **Modes and nodes match in both directions.** A mode added to a copy needs
  a node invoking it; a node invoking a mode needs that mode in the copy; the
  `description:` line names exactly the modes the copy has.
- **Artifacts have one home**: `.awc/tasks/in-progress/<task>/tmp/<file>.md`,
  except `spec.md` and `acceptance-criteria.md` at the trail's root. A new
  artifact is also a row in any validator that lists artifacts.
- **An interviewer keeps its log protocol**: each question logged before it
  is asked, each answer as it arrives, the artifact written only over a
  closed log. That log is the relaunch point.
- **Return signals are a contract.** Rename one and every `expect:` and
  `until:` naming it moves with it.

### Scripts

- **One script does one thing.** A script with internal phases is a workflow
  hiding in a file, where the lead cannot see progress or retry one step.
  `chmod +x`.
- **Quiet when green**; a failure prints the tool's own output.
- **Something runs it**: a `run:` node, an `until_run:`, a `when:`, or a
  node's `Verdict-writer:` argument. Otherwise it is an orphan.

### Launchers

- **Every launch path says the same thing**: the three in-session launchers
  and, for a worktree workflow only, `./<name>.sh` — the same opening role
  stamp, the same input mapping in the same words, the same workflow path.
  A workflow that runs in place has the three launchers and no script;
  `./<name>.sh` exists only where the README's "how to launch" names it.
- **The Claude Code and opencode launchers carry the host's arguments
  placeholder** — a dollar sign followed by the word ARGUMENTS — **exactly
  once**, inside the fenced `<args>` block and nowhere else in the file. The
  host rewrites every occurrence before the model reads the file, so a
  sentence mentioning it turns into the launch arguments. The same
  substitution runs over this skill, which is why the placeholder is spelled
  out here rather than written.
- **The Codex launcher is selected by its `description:`** — keep the trigger
  phrases in it real, and keep them describing what the workflow does.

### README

- **The node table mirrors the YAML**: one row per node, in order, with how
  each exits.
- **"How to launch" matches the isolation**: the script for a worktree
  workflow, the slash command and the Codex trigger phrase for one that runs
  in place.
- **Positive prose.** The package says what the workflow does — never what
  was ruled out, and never what it used to do.

## Ripples — what else moves

| You changed | Also touch |
| --- | --- |
| An input (added, renamed, removed) | every `{{placeholder}}` using it; the three in-session launchers and, where it exists, `./<name>.sh` — their step 3 and the argument hint; the README's inputs table |
| A node added | the agent file (present, mode kept, every argument passed, `expect:` matching); the README row; a `wait:` if it is parallel; the `finish` placement if it touches the trail |
| A node removed | the agent file nothing invokes now; the mode no node asks for; the script and the var only it used; `wait:` lists naming it; the README row; a validator row demanding its artifact |
| A node renamed | `wait:` lists, the README — and a paused run resumes by node id, so check `.awc/tasks/in-progress/` first |
| A var holding a command | the nodes passing `Commands:`; any script wrapping it; the README's scripts section |
| An agent's return signal | every `expect:` and `until:` naming it |
| A reviewer step | `shell` in its scope; the `Verdict-writer:` argument naming `workflows/<name>/scripts/write-verdict-file.sh`; the `when:` guard grepping its verdict file |
| The workflow's name | the folder, the YAML file and its `name:`, the three launcher filenames, the Codex launcher's directory and its `name:` frontmatter, `./<name>.sh` where it exists, every `workflows/<name>/scripts/…` path, the README |

## After the edit — validate

1. The YAML parses. Every `agent:` path resolves from beside the YAML; every
   `run:`, `until_run:` and `when:` script from the launch directory. Scripts
   are executable.
2. Every loop has its cap and one of `until:` / `until_run:`. Every `inline:`
   has its three keys and nothing more. Every `parallel: true` sits on a
   top-level `run:` or `agent:`. Every `wait:` names prior parallel ids.
3. Every agent node passes what its file requires and expects what it
   returns.
4. Every placeholder is declared, and every input, var, agent file and script
   is used somewhere.
5. The three in-session launchers agree — and `./<name>.sh` with them where
   the workflow runs in a worktree — and the arguments placeholder appears
   once in each file that substitutes it.
6. Grep the changed prose for negation echoes and restate them as what the
   workflow does.
7. Walk the node list as the lead would: what happens on each failure, where
   each halt lands, whether any step edits without a verification step after
   it.
8. `ls .awc/tasks/in-progress/` — a live trail resumes by node id, so a
   rename or removal that would strand it is the user's decision, made before
   the edit lands.
9. Commit the package. A worktree workflow refuses to start unless its YAML
   is on `HEAD`.

## When a run halted

| The lead reported | Likely cause | First move |
| --- | --- | --- |
| `blocked -> <step>: asks the lead to write/edit/delete/commit` on an `inline:` node | `agents/workflow_lead.md` predates `inline:` | `awc <agent> --upgrade` |
| `blocked -> <capability>` | `allowed_tools:` drawn too tight | grant what the agent file does |
| `blocked` naming a missing argument or artifact | the node's prompt lacks an argument the agent file requires, or a prior node that produces the artifact | compare the prompt with the file's invocation section |
| a return matching nothing in `expect:` | the copy's signal and the node's `expect:` disagree | align them |
| a loop hit its cap | the escalation worked; the agent's last report sits under `tmp/` | decide with the human, then relaunch and resume at that node |
| a `run:` exited non-zero | the command's output *is* the failure | fix the repo, then resume |
| `halted -> <id>: background agent asked the human` | a parallel step needs the human | drop `parallel: true` from it |

Resuming is a relaunch: the lead asks which node to resume from and confirms
the choice against what is on disk. A node that created commits is never
redone.
